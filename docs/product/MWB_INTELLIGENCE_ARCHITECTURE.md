# MWB Intelligence Architecture (Recommendation)

- **Status:** a recommendation only. Nothing here is implemented by this audit.
- **Constraint:** no AI API. Every piece of intelligence comes from structured Scripture, curated metadata, relationships, local user signals and deterministic algorithms.

## 0. What already exists vs what must be designed

| Area | Already built in Flutter | Must be designed |
|---|---|---|
| Canonical text | KJV and WEB assets, `BibleCanon`, `ScriptureReference` | Stable canonical verse IDs shared by every intelligence object (see §1) |
| Personalisation | Rule model, edit engine, validator, risk, renderer, queues | Person/number/agreement checks; broader contexts; recipient-substitution policy |
| Search | Reference parser, substring AND search, debounce | Inverted index or FTS, ranking, phrases, tolerance, intelligence search |
| Intelligence corpus | 9 passage contexts; 19 mock topics | Promises, situations, prayers, declarations, blessings, relationships, journeys, Daily Word candidates |
| Daily Word | 21-reference rotation and 10 promises | Candidate corpus, 365-day schedule, leap policy, adaptive selector |
| Signals | Recent searches, history, saves, interests (local) | A signal model feeding relevance |

## 1. Canonical identity: one key for everything

- Use `ScriptureReference.compact` (`"PSA 23:1"`, USFM book IDs), which already exists, as the **canonical verse key**.
- Every intelligence object references verses by this key, never by translation text. This is GODSAID's "canonical identity ≠ translation text" rule.
- Ranges are stored as `start`/`end` keys.
- WEB's omitted verses and Romans 14/16 versification differences are handled by the translation layer. Intelligence data is never duplicated per translation.

## 2. Local intelligence corpus (bundled, versioned JSON)

Recommended assets, each with a `schema` and `corpusVersion`:

```
assets/intel/
  contexts.json        speaker, author, audience, addressee type, classification, conditionality
  situations.json      life situations → verse keys, promise ids, prayer ids
  promises.json        verse key, category, reception note, conditions
  blessings.json       text (not Scripture), verse keys
  prayers.json         text (not Scripture), situation, verse keys (≥2)
  declarations.json    text with {name}, verse keys; no gendered pronouns
  relationships.json   [verseA, verseB, type: theme|explanation|quotation|supporting, note]
  journeys.json        ordered steps of typed references
  daily/candidates.json  id, verse key, category, theme, situations[], flags (pool, leap)
  daily/schedule.json    365 assignments (+ leap), generated and checked by a tool
```

Rules:
- **Prayers, blessings and declarations are typed as `nonScripture`.** The UI must style them differently and never attribute them to God.
- **Curation is enforced by tests**, as Phase 3 did historically:
  - every verse key resolves in KJV;
  - every prayer has ≥2 references;
  - no declaration contains *he/him/his/she/her*;
  - no orphan IDs.
- The demo's data (`MY_WORD_BIBLE_MWB_DEMO (1).html` lines 1120–1557) can **seed** this corpus. Every item must then pass editorial review.
- The demo's `mwb` strategies and substitutions **must not** be imported (see `MWB_ORIGINAL_DEMO_AUDIT.md` §4).
- If the historical GODSAID exports (393 candidates, 54 context profiles, etc.) can be recovered, they should replace the demo seed.

## 3. Local Bible search

**Recommendation: a pre-built inverted index shipped as an asset, plus a pure-Dart query engine.** Migrate to SQLite FTS5 only if multi-translation size or features demand it.

| Option | Pros | Cons |
|---|---|---|
| **A. Pre-built inverted index** (term → postings of verse ordinals, per translation, generated by a `tool/` script like `build_web_asset.js`) | No native dependency; deterministic; testable in `flutter test`; ~31k verses is small; instant once loaded | Phrase search needs positional postings (larger) or a verify pass |
| B. SQLite FTS5 (`sqlite3` / `sqflite`) | BM25 ranking, phrase and prefix queries built in; scales to many translations | Native dependency; DB build pipeline; FTS5 availability differs by platform package; harder widget testing |
| C. Current linear scan | Already works | No ranking; slows as translations are added |

Choose **A now and keep the `BibleRepository.search` interface**, so B can replace it later without UI changes.

**Query pipeline (runs on every keystroke after a 120–150 ms debounce, in an isolate):**

1. **Normalise:**
   - lower-case;
   - fold punctuation and curly quotes;
   - treat apostrophes as optional;
   - map archaic forms (`thee`/`thou`/`thy`/`thine` ↔ `you`/`your`, `saith` ↔ `says`) as **search synonyms only, never in displayed text**.
2. **Detect intent:**
   - **Reference** (existing `tryParse`), extended with book-only queries ("Romans" → book) and partial book names ("Phil", "1 Jn").
   - **Quoted phrase** → exact-phrase mode.
   - **Otherwise** → keyword mode.
3. **Retrieve:** look up postings for each term; use prefix expansion for the last token (autocomplete); add edit-distance-1 fuzzy terms for tokens of 5+ characters, from a vocabulary list.
4. **Rank** (deterministic, explainable):
   - exact phrase in the verse: +100;
   - all terms present: +40;
   - terms adjacent, in query order: +25;
   - proportion of terms matched × 30;
   - BM25-like inverse frequency for rare terms;
   - small boost for verses that carry intelligence (promise, Daily Word, situation);
   - ties broken by canonical order.
5. **Group results:**
   - reference jump first;
   - then "Best match" (top 5);
   - then all verses (paged);
   - then intelligence objects (§4);
   - then topics and media.
6. **Context:** show the matched verse with the previous and next verse, available on expand.

## 4. Intelligence search ("Search everything")

- Build a second small index over intelligence objects: titles, categories, keywords, situation names and the text of non-Scripture objects.
- Score it the way the demo does (`fuzzyScore` / `searchAll`, lines 1674–1715): label > keyword > body.
- A query like **"fear"** returns:
  - the life situation *Fear*;
  - its promises, prayer and declaration;
  - the journey *Facing Fear with God*;
  - Daily Word candidates in Courage and Strength;
  - verses containing *fear* / *afraid* / *dismayed* (synonym list curated per situation);
  - topics and media tagged *fear*.
- This is curated association, not inference. Every link is stored in `situations.json` or `relationships.json`.

## 5. Scripture relationships and discovery

- `relationships.json` is a typed, bidirectional, curated graph. Each edge carries a `type` and a short `note` (why it holds).
- Rule: **no edge without a defensible textual or contextual reason** (historical Phase 4 principle).
- Journeys are ordered lists of typed references with step notes (the demo's `PATHS` shape).
- Discovery is navigation through the graph; no similarity scores are computed.

## 6. Daily Word: schedule, adaptive relevance, freshness, diversity

### 6.1 Base schedule (always valid)

- **The schedule is generated offline by a tool and shipped:**
  - a `candidates.json` pool (target ≥ 365 + reserve);
  - a `schedule.json` with 365 assignments, built by category round-robin so no category repeats on consecutive days and no candidate repeats within the year.
- **Feb 29** → the reserved leap candidate (Rev 21:5).
- Index by `month-day`, not by day-of-year, so dates stay stable across leap years.
- **Tests:** 365 distinct, no consecutive category repeats, every verse key resolves.

### 6.2 Signals (local only, on the device)

| Signal | Source that already exists | Weighting |
|---|---|---|
| Interests chosen at onboarding | `interestsProvider` | Long-lived category affinity |
| Searches | `recentSearchesProvider` | Mapped to situations and categories via the curated keyword table |
| Reading | `readingHistoryProvider` | Book/chapter → categories via the intelligence index |
| Saves, highlights, notes | Library controllers | Verse keys → categories and situations |
| Prayer opened, situation viewed | *(new)* | Situation affinity |
| Recently shown Daily Words | *(new)* `daily.history` | Freshness |

Signals decay with time (half-life about 7 days). The user can view and clear them in Profile → Privacy. Nothing leaves the device.

### 6.3 Selector (deterministic, explainable; no AI)

```
candidates = pool − shownInLast(N=60 days)                  // freshness
score(c) = 50·categoryAffinity(c) + 40·situationAffinity(c)
         + 10·interestMatch(c)
         − 15·[c.category == yesterday.category]              // diversity
         − 30·[c.category shown ≥3 times in last 7 days]
if no signals or max(score) ≤ threshold → base schedule      // fallback
tie-break: hash(dateKey + candidateId) ascending              // deterministic per day
```

- **The pick is stable for the day:** stored on first computation, like the demo's `DailyState.log`.
- **Yesterday** is what was actually shown. **Tomorrow** is the base schedule, labelled "scheduled". It must not be presented as a promise of what will be shown.
- **Every pick carries reason tags** ("Because you searched *anxiety*"). Wording must never claim divine selection. Use "Selected for you from Scripture on *peace*", not "God's message for you today".
- **The MWB layer applies after selection.** If the verse has an approved rule in the active edition, render it; otherwise show the source text. The selector never prefers verses just because they can be personalised.

## 7. Personalisation integrity (engine changes to design, not to make now)

Validator additions needed before the rule set grows beyond vocatives:

1. **Pronoun person and number guard.** Any `replace` edit whose anchor contains a person-carrying pronoun (*I, me, my, mine, we, us, our, ours, ye, you, your, thou, thee, thy, thine*) is an **error** unless every remaining pronoun of the same referent in the verse is handled and a reviewer note is recorded.
2. **Agreement check.** After replacement, a name followed by a plural verb (*are, were, have, do* and the like) is an error. A name followed by an archaic second-person verb form (*art, hast, shalt, wilt*) is flagged.
3. **Residual-pronoun consistency.** If any `we`/`us` remains after a `we`→name edit, flag `personInconsistent`.
4. **Context required to pass.** Missing passage context should block an *automated pass* for any `replace` operation, not just warn.
5. **Collective and covenant guard.** An addressee of `collective` combined with a replacement gives at least high risk and requires review notes.
6. **Speech-frame guard.** Never insert a vocative into narrative frames such as "X said unto Y" (demo defect D3).
7. **Capitalisation guard.** Never lower-case a source character (demo defect D2). The edit engine already preserves case because it inserts rather than rewrites.

**Permanent regression fixtures (to be added in a later, authorised stage):**
- Eph 2:10 cases A–D from `FLUTTER_IMPLEMENTATION_AUDIT.md` §5. All must be rejected or flagged.
- Heb 4:16 corporate "Let us".
- John 11:25 speech frame.
- Ps 23:1 first-person psalm.
- Jer 29:11 collective exile audience.
